## Memory map (while Python runs)

Interrupts are off, the CPU stack is 16-bit (`$1800-$1DFF`), the base page is `$16xx`, and
the ROMs are unmapped (MAP clear, `$01 = $35`, no `$D030` ROM bits). `kernal_call` puts the
boot state back for one KERNAL call: MAPHI `$E000` from `$30000` (`ldz #$83`), the boot `$01`
and `$D030`, B = 0, the page-1 stack, `cli`. Afterwards it puts back the VIC-IV's screen
and character set pointers (`$D060-$D063`, `$D068-$D06A`) as they were: the KERNAL
changes them (a LOAD of a missing file resets the character set to `$021800`), and a
program may be showing the graphics screen.

The KERNAL's areas are left alone, as the MEGA65 book's chip RAM map asks:
`0.0002-0.15FF`, `1.0000-1.1FFF` (DOS), `1.F700-1.F7FF`, `1.F800-` (colour RAM window)
and `0.FF00-0.FFFF`. The NMI/IRQ vectors there are saved at boot and put back for every
KERNAL call.

Runtime code runs with R in the window. The compiler and the editor run with C in the
window (`compile`, `ovl_compiler`). R and its tail are written back to attic before C
replaces them, so R's variables survive a compile in the middle of runtime code (a
module imported by a key function, say); C keeps nothing between compiles. A variable
that resident code uses while C is in must not live in R.

Tails: with R in, the window's last 4 KB (`TAIL`) holds one of eight tails (A, B, H, F,
S, P, I, X), swapped by a 4 KB DMA from attic (`need_tail` in `resident.asm`; `ovl_runtime`
brings back R with tail A). Code reaches a tail routine only through a stub,
`label: #TAILCALL TAIL_x, target` (6 bytes: `jsr tcall` and the data; the `#TAILA`,
`#TAILB`, `#TAILF`, `#TAILS` macros make them). `tcall` (`tailcall.asm`) loads the tail,
runs the target and, when it returns, loads the tail that was in before, passing A, X,
Y and the flags through both ways. So tail code may call anything, including other
tails' stubs and Python code: a nested Python call can bring in other tails, and
`vm_call_nested` puts its caller's tail back when it returns (as does `it_inst`'s
exception catcher). A tail keeps its variables like ordinary memory: while tail
routines are running (`tail_depth`, counted by `tcall`), a tail that leaves the window
is written back to its attic image first, so a routine swapped out in mid-call finds
them as it left them. What tail code must not do is call into another tail directly
(not through a stub), or leave a tail routine other than by returning (`jmp vm_loop`
from an opcode handler: those stay in R).

Placing code: resident part 1 (`$2001-$7DFF`) is for what the compiler, the REPL and the
VM's core need, also while overlay C is in. Runtime code goes in overlay R, cold
runtime code in a tail. More tails cost nothing but 4 KB of attic each (and a DMA when
one is swapped in): add one in `platform.asm` (`OVL_x_ATTIC`, `TAILS_N`),
`resident.asm` (`TAIL_x`, `tail_src`) and `main.asm` (both passes).

Builtins read their arguments from `argv` (`nargc` of them, `npos` positional, `nkw`
keywords named by `kwnames`). Python code a builtin runs (a key function, `__str__`, a
user `__next__`) makes native calls of its own, which reuse those; `vm_call_nested`
saves the caller's set on the CPU stack and puts it back afterwards
(`NATIVE_SAVE`/`NATIVE_RESTORE`, also around `it_inst`'s catch), together with its
tail. So a builtin can read its arguments at any point. `argc` is the count for the
next call (the VM's, or one the builtin makes through `vm_call_nested`). Registers
(`r0`-`r3`, `t0`-`t7`) are not saved: keep values that must survive Python code on the
value stack or the CPU stack.

Boot: the program file holds part 1, overlay R (already in the window, with tail A) and
part 2 (at `$D000`, DMA'd to `$F000`). `mpy-ovl` holds overlay C and the other tails
(one after the other, copied to attic in one DMA); it is
loaded to `$50000` and the pieces go to attic. The window (overlay R) is copied to attic
too.

## Values

A value is a 16-bit ref:

* odd: a small int (`ref >> 1`, signed 15-bit)
* 0: NULL (an unbound local; never visible to Python)
* 2 / 4 / 6: None / False / True
* otherwise: the object at `$40000 + ref` (even aligned)

Object header: type, flags (mark, perm, interned), size (word). Layouts are listed at the
top of `heap.asm`. Compile-time objects (constants, names) are allocated "perm" and never
freed. `run()` and `new()` reset the whole heap.

Native code passes refs in A (lo) / X (hi). Anything that allocates can collect garbage.
Refs that must survive go in `r0`-`r3`, `groot`, or on the value stack: those are roots.
The `t` registers are clobbered by allocation (the lexer allocates when it interns a new
name), and so are `p0`-`p3` and `fp0`-`fp2`. A count, index or ref that must live
across an allocation, or across a call that may run Python code (`vm_call_nested`,
dunders, `__eq__`, `__hash__`, iterators), goes on the CPU stack, in a static byte, or
(refs) on the value stack. Never keep a new object only in `r1` or on the CPU stack
while the next allocation happens. Re-derive pointers such as `fp0` (`self_str`)
after the allocation.

`heap_init` (`run()`, `new()`) clears every root (`groot`, `r0`-`r3`, `cur_exc`, ...).
An exception can leave a `groot` slot set, and the stale ref would otherwise point into
the middle of an object of the next program, where marking it sets bit 7 of a size or
length byte.

`run_tests.py --gc` pokes `gc_stress` (heap.asm), so the allocator collects before
every non-perm allocation. Most bugs of this kind show up at once in that mode. Each
collection runs while about 50 KB of the heap is live, so a stress run takes minutes per
test.

The GC does not move objects. Many live small objects with free holes between them can
leave no hole big enough for a larger request: the allocator then raises `MemoryError`
after two collections (`al_tries`) even though `mem()` shows space free.

## Bytecode and calls

Stack machine, one opcode byte plus operands (see `opcodes.asm`; `tools/disasm.py` decodes
it). The value stack grows down from `$F000` and `vsp` points at the top. Locals of a
function are contiguous: local `i` is at `vfp + 2*(nlocals-1-i)`, which is the operand of
`LOAD_FAST`/`STORE_FAST`. A function's locals are found by a token pre-scan of its body
(`prescan`).

Calls: `CALL n` has `[f][a0]..[an-1]` on the stack. `LOAD_METHOD`/`CALL_METHOD` push
`[meth][self]` or `[callable][NULL]`. Builtins get their arguments copied to `argv`.
Python functions get a frame (return ip, caller `vfp`, result slot, flags). A native
routine that calls Python (`vm_call_nested`) starts a new run level. An exception that
leaves a level unwinds the CPU stack to the level outside it.

Exceptions: `SETUP_EXCEPT` pushes a handler (ip, vsp, frp, vfp); `throw` resets the CPU
stack to the run level and jumps to the newest handler of that level. `RETURN` drops the
handlers of the returning function.

Native code can catch an exception too: `it_inst` (a user iterator's `__next__`,
`seq.asm`) pushes `ip`, `vsp`, `vfp`, `err_sp` and `err_vec` on the CPU stack and points
`err_sp`/`err_vec` at itself. An exception that leaves the nested run lands there:
`StopIteration` ends the iteration, and anything else is thrown on with the outer
context restored.

Calling an instance (`do_call`, `vm_call_nested`) looks up `__call__` with
`get_method` and inserts the instance as argument 0 (`inst_call`).

## Compiler notes

* Assignment targets are found after the fact: an expression is compiled as loads; on
  `=` the last load turns into a store. Targets that must be stored after the value
  (tuples, chains, for-loop targets) have their prefix code cut to the attic cut stack
  and pasted back later (`cut_code` / `paste_code` relocate jumps).
* Comprehensions and conditional expressions move code the same way: the element (or
  the `x` of `x if c else y`) is compiled first, then cut and pasted where it runs.
* `try` always emits three NOPs that become an outer `SETUP_EXCEPT` when a `finally`
  follows; the finally block is compiled twice (the lexer state is saved and restored).
* f-strings: the lexer returns the raw text, and the compiler compiles each `{expr}` by
  pointing the lexer at it.

## Floats

IEEE doubles: a `T_FLOAT` object holds the 8 bytes. Arithmetic unpacks them into
12-byte registers (`fa`..`fi`: class, sign, 16-bit exponent, 64-bit mantissa) and keeps
results truncated to 64 bits with a sticky bit, so packing rounds each operation to
nearest-even like IEEE hardware. The 128-bit product uses the hardware multiplier;
division, `fmod` and `sqrt` are bit-by-bit. `//` and `%` follow CPython's `float_divmod`.

Decimal conversion is exact, with bignums (`fbig.asm`):

* text -> double: up to 30 significant digits (more set a sticky bit); `D * 10^E` is
  either an integer (its top 64 bits) or a long division by `10^-E` (64 quotient bits).
* double -> text (`f_digits`): Steele & White / Burger & Dybvig. Mode 0 gives the
  shortest digits that read back as the same double (repr); modes 1 and 2 give a fixed
  number of digits or decimals, rounded half-to-even on the exact value. `round(x, n)`
  is mode 2 followed by text -> double, as in CPython.

The math functions reduce the argument (`n ln 2`, `n pi/2` with constants split into
parts) and sum a power series in 64-bit precision, so most results are correctly
rounded. CPython's results come from the platform's C library and can differ in the last
digit (MSVC's `cos(1)` is one ulp off, for example), so `tests/t_floats.py` rounds them.

`math` is a class object (made by `math_init`, perm) whose dict holds the functions and
constants; `import math` returns it (`import_math`).

## Files

`open()` makes a `T_FILE` object for a SEQ file on drive 8, opened through the KERNAL as
logical file 2-5 (`file_used` in `disk.asm` tracks them; `py_reset` closes them all).
The name goes to the drive as `name,s,r` (`,s,w` with `@0:` in front to replace, or
`,s,a`), and the command channel (15) tells whether that worked: 62 becomes
`FileNotFoundError`, other errors `OSError` with the drive's message.

Bytes move in blocks of up to 255 through `FNAMEBUF` (`$1E00`): `kio` (in `disk.asm`,
below `$8000`, because the KERNAL's DOS maps itself in above that) runs the
`CHKIN`/`CHRIN` or `CHKOUT`/`CHROUT` loop inside one `kernal_call`. Reading refills the
file's 256-byte buffer from there. When the KERNAL reports the end of the file and the
buffer is empty, the KERNAL file is closed at once (so `open(x).read()` and
`for line in open(x)` give their channel back without `close()`).

`os` is made at its first `import` (perm, like `math`; `os_mod` is cleared by
`py_reset`), with `os.path` in its dict. `remove`/`rename` send `S0:name` / `R0:new=old`
on the command channel and read the result (`01, FILES SCRATCHED,nn` with nn = 0 means
no such file). `listdir` and `path.exists` load `$` and take the quoted names.

## Modules

`import name` (`mod_import`) tries `math` and `os`, then the hidden global `"name."`,
which holds the module object once it is imported. Otherwise it loads `name.py` to
`MODSRC` (`xm_load`, tail F; failing that `lib-name.py`, where `xm_alias` shortens a
long name such as `statistics` to `stats`, the same table as `tools/mkpy.py`'s
`ALIASES`), binds a `T_MODULE` object there, compiles the source after the running code
(the compiler overlay comes in and goes out; a compile error comes back through an error
context that restores the runtime overlay first), and runs the module's top level as a
nested VM run. `c_made_func` is set so the REPL keeps the new code.

While a module is compiled (`c_mod` set), every global name compiles to a hidden symbol
`"name.x"` (`gsym`), and `SYM_BASE` remembers its plain symbol. `LOAD_GLOBAL` of an
unbound hidden symbol tries the plain one: that is how a module reaches the builtins.
A module's attributes read and write its hidden symbols.

`py_reset` (boot, `run()`, `new()`) is in tail I with the exception setup; only its
call of `builtins_init` stays outside (that brings in tail B for `math`).

## Dicts

A dict (`T_DICT`, 12 bytes) keeps its pairs in insertion order in a `T_ARR` (`+4` count,
`+6` capacity, `+8` the array), which iteration, `repr`, `==` and the GC walk. From 8
pairs it also has a hash index at `+10` (`dicthash.asm`): a `T_ARR` with the mask at `+4`
and 2^n 16-bit slots (0 = empty, i + 1 = pair i), open addressing with linear probing,
kept below half full. `dict_find` hashes the key (`obj_hash`) and probes, comparing by
identity and then `==`; smaller dicts (most instance and class dicts, keyword arguments)
are searched pair by pair (`dict_scan`). `dict_set` enters a new pair in the slot the
failed search found (`dict_index_add`) or rebuilds the index when it would be half full
(`dict_reindex`, to more than twice the pairs); `dict_del` moves the later pairs down
and rebuilds it. `clear` drops it.

`obj_hash` gives 16 bits, equal for `==` keys across types (`1`, `1.0`, `True`: floats go
through `float_hash`, so they hash like the equal int), tuples combine their items,
frozensets use their size, instances call `__hash__` or use their identity.
`need_hashable` rejects lists, dicts, sets and instances with `__eq__` but no
`__hash__`, for every lookup, so small and big dicts agree. Both may run Python code
(`__hash__`, `__eq__`), which is why `dict_find` keeps its probing state on the CPU stack
around them, and why `op_in` keeps its operator there across `contains`.

Dict and set iterators (`IT_DICT`, `IT_ITEMS`, `IT_VALUES`) hold the size at creation
(`+12`), the keys left (`+14`) and the last key returned (`+16`, which the GC marks as
well). `it_dpair` (overlay R, `methods.asm`) raises "changed size" when the size differs.
Because `dict_del` moves pairs down where CPython leaves a hole, it puts the position
back after the last key: it finds that key again, or steps back one place if the key
itself was deleted. Finding a key when none are left raises CPython's "dictionary keys
changed during iteration" (dicts only; sets never raise it).

## Closures

The compiler is single-pass, so a function's shared variables must be known before its
body is compiled. Its pre-scan (`prescan`; `lambda_scan` for a lambda) notes every name
used inside nested `def`/`class` bodies and lambdas (`ps_inner`); `fb_cells` makes the
function's locals with those names cells (`SC_CELLMAP`; a nested function's own variable
of the same name makes an unneeded cell: slower, not wrong). A function with cells, or
nested in another function, gets a hidden last local, the environment (frame offset 0).

At run time (`env.asm`) the environment is a tuple: item 0 its parent, then the cells.
`ENTER_ENV n` (the body's first instruction) makes it from the function's closure
(`T_FUNC` `+14`); with no cells the closure itself is the environment. Parameters that
are cells are copied into them next. `MAKE_FUNCTION` in a frame with an environment is
followed by `SET_CLOSURE`, which gives the new function that environment.
`resolve_name` turns a name into a fast local, a global, or `LOAD_DEREF`/`STORE_DEREF`
(depth, cell): the depth counts the function scopes with cells between the frame's
function and the one that owns the cell (class scopes are skipped: a class body runs in
its function's frame). `nonlocal` names are kept out of the locals and must resolve to
an enclosing cell (SyntaxError otherwise).

## Decorators, staticmethod / classmethod / property, class bodies

`@d` lines compile their expressions first (they stay on the stack), then the def or
class; `CALL 1` per decorator, innermost first, comes before the store of the name
(`st_decorated`, `SC_NDECO`). The REPL's `needs_more` continues after an `@` line.

`staticmethod`, `classmethod` and `property` make `T_DESC` objects (`desc.asm`: +4
kind, +6 function or getter, +8 setter). `get_method` passes what it finds in a class
to `desc_resolve` (instance attribute: functions bind self, a staticmethod gives its
function, a classmethod binds the class, a property calls its getter) or `desc_class`
(attribute of the class itself). A store into an instance attribute asks `desc_store`
first, which looks for a property only in classes flagged `F_PROPS` (set when a
property is stored in a class, inherited by `MAKE_CLASS`), so plain stores stay cheap.

A class body runs in its function's (or the module's) frame, with the class on the
VM's class-body stack (`cb_stack`: `MAKE_CLASS` pushes the class and its value-stack
slot, `END_CLASS` pops). A body left by an exception leaves its entry behind. Entries
whose slot is at or above the current stack top are stale, and `MAKE_CLASS` /
`LOAD_CLASSNAME` drop them (`cb_prune`). Its names
load with `LOAD_CLASSNAME`: the class's own attribute if it has one, else the global, so
`b = a * 2` and `@x.setter` see what the body defined before.

## *args, **kwargs, keyword-only parameters, f(*a, **k)

A function's parameters are its first locals: the positional ones, `*args`, the
keyword-only ones, `**kwargs` (`T_FUNC` `+18` flags, `+19` keyword-only count, `+16`
their defaults with NULL for required ones; `MAKE_FUNCTION` has two more operand
bytes). `call_py` binds plain functions as before (`kw_to_positional`, defaults); one
with any of these goes through `bind_ex` (tail X, `args.asm`), which reads the
arguments in place, builds the `*args` tuple and `**kwargs` dict while they are still
on the stack, fills defaults, raises the argument errors, and only then replaces the
arguments with the parameters in order.

A call with `*` or `**`: the arguments before the first one compile plainly, then
`PACK_ARGS` turns them into a list and a dict; each later argument goes in with
`EX_ARG` (append, extend, keyword, merge). `CALL_EX` pushes the list items and the dict
values with a tuple of the (interned) keys as `kwnames`, then calls as `CALL_KW` would.
It leaves that tuple under the callable, so it stays referenced during the call (the
GC does not see `kwnames`); `ROT2`, `POP` after the call drop it. The compiler keeps
each call's argument state per nesting level (`ca_*`), so keyword names of a call
inside another call's arguments do not mix.

## Generators

The pre-scan notes a `yield` in the body; the function gets `FF_GEN` (`T_FUNC` `+18`),
and `call_py` binds its arguments as usual but then makes a `T_GEN` object
(`gen_create`) holding its locals in a tuple, instead of running it. `yield x` is
`YIELD_VALUE`, whose result is the value sent in; `yield from it` compiles to a loop
(`GET_ITER; FOR_ITER; YIELD_VALUE; POP; JUMP`).

`gen_resume` (`gen.asm`) rebuilds the generator's part of the value stack as
`[generator][result slot][locals][temporaries]`, so `vfp` is the result slot minus
`2 * nlocals`, pushes a call frame flagged `FR_GEN`, and runs on at the saved ip.
`FOR_ITER` resumes a generator inline (`FR_FORIT`: no native recursion, so deep
`yield from` chains are fine); native code (`iter_next`: `list()`, `sum()`, `next()`,
`send()`) resumes it in a run level of its own (`FR_NESTED`, like `vm_call_nested`).
`YIELD_VALUE` copies everything under the result slot into the generator, and the
handlers of its frame (relative to the result slot, in a raw `T_ARR`: tail X does that
copying, only when there are any), then returns like `RETURN`; a `RETURN` in a
generator frame finishes it (`gen_return`). An exception that leaves a generator drops
its frame without telling it: it still says running, and `gen_alive` checks whether its
frame is really still on the frame stack. `ENTER_ENV` reads `c_func`, so starting a
generator sets it to the generator's function.

`yield from it` compiles to `GET_ITER; None; t: SEND x; YIELD_VALUE; JUMP t; x:`.
`SEND` resumes a generator inline with the value under it (`FR_FORIT | FR_SENDX`:
when it finishes, its return value replaces it and `SEND` jumps to `x`), or takes the
next item of another iterator. `throw()` and `close()` set `gen_exc`, and the resumed
generator raises it at its `yield`, where its own handlers (restored with its frame)
see it. `close()` catches what comes back out with `try_call` (`seq.asm`, part 2: a
native call under an error context of its own, as a user iterator's `__next__` runs
too): `GeneratorExit` or `StopIteration` is a clean close. A generator that finishes
for native code returns its return value with the carry set; `next()`, `send()` and
`throw()` raise `StopIteration` with it as `.value` (`xg_stop`).

A generator resumed with an exception while it waits in a `yield from` (the instruction
after its `YIELD_VALUE` is the `JUMP` back to `SEND`) passes it on: `gen_throw_at` pushes
it and sets `send_throw`, and `SEND` resumes the inner generator with it as its
`gen_exc` (an iterator that is not a generator gets it raised in the outer one).
PEP 479: `vm_except` first calls `gen_p479`, which raises `RuntimeError` instead when a
`StopIteration` is about to unwind past a generator's frame.

`iter_next` callers must not keep A/X when it says "exhausted" (C set): `it_enum` put
them in `r3`, a GC root, and the next collection marked whatever that pointed at.

A generator expression is a generator function of its own, as in CPython (`genexp`):
the element was compiled before its `for` showed up, so its code is dropped and the
lexer goes back to it (`lx_push` at the element). The first iterable is compiled in
the enclosing scope (`ge_to_iter` finds it), then `MAKE_FUNCTION <genexpr>` with one
parameter (`" 0"`), whose body is the comprehension code (`comprehension` kind 2) over
that parameter, yielding each element; `ROT2`, `CALL 1` make the generator. Its `for`
targets are its locals (`ge_scan`). The enclosing function's pre-scan must make the
names a generator expression uses cells: names inside brackets wait in `ps_pend` until
a `for` shows that their `(` group is a generator expression (`ps_gfor`); a lambda with
a comprehension in it makes all its parameters cells.

Type numbers: sets and frozensets (`T_SET`, `T_FSET`, which only `type_of` returns) must
stay the last types, because code tests `>= T_SET` for "a set or frozenset".

## Sets

A set is a `T_DICT` object (members are the keys, values `None`) with `F_SET` in its
header flags, and a frozenset also has `F_FROZEN`. `type_of` returns `T_SET` / `T_FSET`
for them, so code that dispatches on `type_of` (subscripts, dict methods, `isinstance`)
does not take them for dicts, while code that reads the header byte itself (the GC,
truth, `len`) handles them as dicts for free. `in`, iteration and `==` (`dict_eq`: a
set equals a frozenset with the same members) use the dict code.

`{a, b}` and `{x for ...}` compile to a list and `BUILD_SET`, which turns the list on
top of the stack into a set. The operations (`set_op`: union, intersection, difference,
symmetric difference) build a new set from lists of members on the value stack; a
member's `__eq__` may run Python code at any point. The in-place methods
(`update`, ...) compute the result and let `self` take over its count and pair array.

## with

`with m as x: body` stores the manager in a hidden variable (`" w<n>"`: a name no source
can spell; in functions the prescan makes it a local, one per manager), calls
`__enter__`, and compiles the body under `SETUP_EXCEPT`: the normal exit calls
`__exit__(None, None, None)`; the handler calls `__exit__(type(e), e, None)` and swallows
the exception (`POP_EXCEPT`) if that returns something true, else re-raises it.
`with a, b:` is compiled as `with a: with b:` (`with_item` recurses).

Leaving blocks early: the compiler keeps an exit stack (`xb_*`) of the open `try` and
`with` blocks, each with the handlers it holds at that point (a try body 1, or 2 with a
`finally`: the outer handler too; the `except`/`else` clauses of a `try` with `finally`
1) and its exit code. `break`/`continue` (down to the loop's level, kept in its loop
record) and `return` (the function's blocks) emit, innermost first, each block's
`POP_BLOCK`s and then its exit code: the `__exit__` call, or the `finally` body compiled
again in place. `try_scan` finds the `finally` clause when the `try` starts (skipping
the body and the other clauses) and keeps the lexer state at its `:` (`fin_lx`).

Sets are in tail T (`sets.asm`); overlay R keeps `BUILD_SET`'s handler and the stubs
(`setsr.asm`).

## Debugging

* `tools/xemu_run.py SHOT.png prompt "type:1+1\n" screen log`: headless runs.
* `tools/trace.py hold STEPS "line" ...`: arms the `DBG_HOLD` point in `vm_except`, then
  single-steps with the monitor (`t1`, `t`). Xemu's `b` breakpoints did not stop the CPU.
* `tools/bisect_run.py file.py`: pokes growing prefixes of a program into the source
  buffer and runs them to find the line that breaks it.
* Lessons learned: anonymous `+`/`-` labels caused several bugs (use named labels in
  branchy code). `PUSH`/`POKE` preserve A. Keep string-builder marks on the CPU stack, not
  in `t5`.
